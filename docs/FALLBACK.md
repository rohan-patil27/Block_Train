# Deterministic Fallback Strategy

## Overview
The Gatidhara Phase 5 implementation includes a heuristic, rule-based fallback scheduler. This guarantees a mathematically valid and deterministic schedule even if the CP-SAT optimizer timeouts or yields infeasible status.

## Fallback Logic Formulation
The fallback mechanism uses a greedy scheduling approach:
1. **Priority Sorting**: All pending `OptMaintenanceRequest` items are sorted by their `priority_score` (descending).
2. **Sequential Assignment**: For each maintenance request, the scheduler attempts to assign it to the earliest possible time window within its `available_windows`.
3. **Conflict Avoidance**: The time window assignment strictly avoids overlapping assignments for the same `section_id` with previously scheduled requests in the fallback run.
4. **Duration Enforcement**: The scheduled duration matches the request's exact required duration.
5. **ID Allocation**: Fallback groups are identified with the "FB-" prefix.

## Critical Rules
- **No Optimization Guarantee**: Fallback does NOT optimize for synergies (like shadow-blocks) or global objective maximization.
- **Safety Validated**: Plans generated by the Fallback Scheduler MUST pass through the Safety Validator before being recommended or stored.
- **Explainability Interception**: The `ExplanationGenerator` explicitly highlights when a plan was generated by the fallback strategy.
